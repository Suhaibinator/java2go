# Equal-scale BigDecimal comparison: measured allocation evidence

The optimization compares coefficients directly when scales match, after both null checks. Different scales use the existing comparison. In the measured generated-Go workloads this eliminates temporary allocations for equal-scale comparisons. **No CPU speedup or superiority over Java is claimed.** These are allocation counts, not allocated bytes or retained heap.

This package contains the exact measured shared Java source, native drivers, allocation/semantic harnesses, runtime patch, compact evidence, and a focused reproduction script. It excludes the older unexecuted shared preparation and verbose logs.

## Correctness scope and provenance

The historical private run passed both complete runtime suites and race suites, plus all six BigNumber JDK oracle groups for each variant. Three seeds (17, 97, 65537) × three modes × Java/baseline/candidate produced **27 workload processes** with exact stdout **and stderr** agreement. Each used 128 pairs and eight repetitions. One compiler produced identical generated bytes for the two Go runtimes.

The probe covers negative/positive/zero coefficients; long coefficients; extreme scales expressible through the supported string constructor; left/right text/hash/scale immutability; distinct constructor identity; comparison symmetry; scale-sensitive equals; null receiver, argument, and both; and argument evaluation counts. ## Declared configuration and preserved failure

JDK 21.0.6 at `/Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home`; `LANG=LC_ALL=en_US.UTF-8`, UTC. Go settings: `GOMAXPROCS=2`, `GOMEMLIMIT=256MiB`, `GOGC=100`, writable campaign cache and `/private/tmp`. JVM workload flags: Serial GC, two active processors, Xms32m/Xmx256m. These are comparable configured bounds, not identical collector policies.

A prior **C-locale** baseline oracle failed: the JVM's error text contained `NumberFormatException:For input string: "?"`, while generated Go contained `NumberFormatException:For input string: "𝟙"`. A local JDK `-XshowSettings:properties -version` diagnostic confirmed native/stdout/stderr **US-ASCII** under C and **UTF-8** under en_US.UTF-8; file.encoding was UTF-8 in both. The C-locale discrepancy remains a pre-existing compatibility limitation, not a passing test or merely an infrastructure failure. UTF-8 acceptance does not erase it. An earlier home-cache permission failure is recorded separately in the compact evidence.

## Focused reproduction

Provide a pre-optimization repository checkout, such as **11d55eb**, whose BigDecimal source matches the pinned baseline hash. Coordinate a measurement slot first, then run:

```sh
python3 PATH_TO_THIS_PACKAGE/reproduce.py --baseline /absolute/path/to/baseline-checkout --released
```

The script makes private copies; changes only candidate BigDecimal; compiles one compiler; builds identical generated source against both runtimes; checks the runtime regression and the shared null/immutability oracle; compares both streams for 27 executions; and records three allocation trials per variant. It checks copied sources and input hashes, records generated hashes, and checks source/module hashes after execution. It does not mutate the supplied checkout, run Git, or time CPU performance. New compiler versions may change generated bytes; that difference is recorded and must be disclosed rather than silently treated as exact historical reproduction.

Builds are capped at 300 seconds, executions at 60 seconds, with a 900-second aggregate cap and process-group termination on timeout. Commands, exit status, timeout flags and both output streams/hashes are retained in the printed temporary output directory. The compact script reproduces the focused evidence; it is newly packaged and has not itself been executed. It does not replace the historical full runtime/race/JDK-group gates or the coordinator's current-branch application gates.

For additional current-branch validation, run the full runtime/race suites and `TestCampaignRuntimeBig*` oracle groups under the same declared environment. Future CPU comparisons require a separately scheduled workload with nonconstant inputs, matching operation counts/cores/heap budgets, fresh-process repetitions, and warmed JVM steady-state results reported separately from startup. No such CPU comparison is included here.
