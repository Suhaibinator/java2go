# Sol checkpoint 163: avoid unrelated method synthesis in namespace scans

The full Netty compiler profile identified repeated method synthesis in superclass namespace queries as a major cost. The scanner now reuses the AST node kind and checks a conservative method-name predicate before constructing parameter/body metadata. Only proven name mismatches skip synthesis. Both visibility spellings and possible execution-name prefixes retain the original synthesis and collision allocator; raw identifier and nested-declaration traversal remain unchanged. Unknown, erroneous, edited, missing or out-of-range syntax uses the original path. No cache or dependency-specific shortcut is added.

Sol froze actual allocation/native-call baselines and improvement budgets before production. The previous implementation failed those budgets. The repaired implementation passes semantic differential tests against the unchanged original scanner and reduces work on the tested namespace queries. For the 64-method/24-statement/formal case, scanner work fell from 67,538 allocations and 99,072 native calls to 25,124 and 38,277. This is compiler micro-work evidence, not application speed or full Netty throughput evidence.

The donor revision passed 93 selected compiler parents, runtime/symbol/parser suites, default/F1 build/test compilation/lint and 45 accepted applications. Every before/after generated-Go file set and full byte content is identical. The coordinator independently rehashed all 974 receipts and all 45 generated-Go comparisons. A separate read-only reviewer found no valid-method false-negative or skipped semantic-diagnostic path in the predicate.

The coordinator then reconstructed the sparse patch and inverse against current code, including the covered-child maintenance fix. All seven new query parents pass; five semantic parents also pass twenty race runs each. Default and actual f1_os_profile all-package race builds, test compilation and lint pass.
